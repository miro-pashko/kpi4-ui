Ten elements every interface is assembled from

Screens look endlessly varied, but the parts they are built from are few and old. Each element answers one question and no other: pick one, pick several, type something, go somewhere, see more, make it happen. What follows is the theory of those ten parts — what each one is, the conditions under which it is the right choice, the conditions under which it is the wrong one, and the markup it is written with.

01

Radio button

A small circular control that takes one choice out of a set where every option is visible at the same time.

Radio buttons work only in groups. Each button in a group carries the same name, and that shared name is what enforces the rule: selecting any member clears whichever member was selected before. A lone radio button is a design error, because nothing can ever deselect it once it has been chosen.

The defining property is that all options are on screen together. The reader compares the full set before committing, which makes radio buttons the right tool whenever the wording of the options is part of the decision — the difference between "Standard, 3–5 days, free" and "Express, next day, 60 ₴" is exactly what the person is weighing up. A group should also arrive with one option already chosen, normally the safest or most common, so that the form has a valid state from the first moment.

Use when

  • The options genuinely exclude one another.
  • There are roughly two to six of them.
  • The options need explaining, not just naming.
  • Comparison matters more than saving space.

Avoid when

  • The list is long — fold it into a dropdown instead.
  • More than one answer can be true — those are checkboxes.
  • The choice is a simple on/off — that is one checkbox, or a switch.

Accessibility The fieldset and legend are not decoration. Without them a screen reader announces three unrelated options and never says what the question was.

02

Checkbox

A square control holding one independent yes/no value, ticked and unticked on its own terms.

Checkboxes placed together may look like a group, but ticking one never alters another. That independence is the entire difference from a radio button, and the reason the shapes differ: a circle means the choices push against each other, a square means they do not. The convention is old enough that people read it without thinking about it, which is why swapping the shapes is such an expensive mistake.

A checkbox has a third state besides checked and unchecked. When a parent checkbox governs a list and only part of that list is ticked, it shows an indeterminate state, drawn as a dash rather than a tick. This state cannot be set in HTML; it exists only as a property in script, since it describes a relationship between controls rather than a value to be submitted.

Use when

  • Several options may be true at once: filters, features, notification channels.
  • One statement needs agreement: terms of service, a mailing list.
  • A parent needs to govern a list of children.

Avoid when

  • Exactly one answer is allowed — use radio buttons.
  • The change takes effect instantly on a setting screen — a switch communicates that better.
  • The label needs a negative: "Don't hide unread" forces two negations to be untangled.

Convention Label a checkbox with the state it produces when ticked, phrased positively. The reader should be able to read the label as a sentence that becomes true the moment the box is filled.

03

Text input

A field that accepts typed characters — a value the interface could not have offered in advance.

Everything else on this page narrows a decision down to something the designer anticipated. A text input does the opposite: it accepts a name, an address, a search term, a sentence of complaint. That openness is its strength and its cost, since anything typed may be misspelled, malformed, or deliberately hostile, and must therefore be validated before it is trusted.

The type attribute is the cheapest improvement available. Setting it to email, tel, url, number or search changes the on-screen keyboard a phone offers, enables free browser validation, and tells password managers and autofill what the field holds. Field width should match the expected content: a postcode field as wide as a postcode is a hint delivered without a word of instruction. Anything longer than a single line belongs in a textarea.

Use when

  • The set of valid answers is unbounded or very large.
  • The value is personal: a name, a message, a search.
  • Typing is genuinely faster than choosing from a list.

Avoid when

  • The answer comes from a fixed list — typing only invites typos.
  • Dates, times and quantities have purpose-built controls.
  • The placeholder is being used in place of a label; it disappears exactly when it is needed.

Principle A constraint that exists should be visible before it is broken. A character limit, a required format or a minimum length belongs in helper text under the field, not in an error message that appears after the work has been done.

04

Tabs

A row of labels over a single panel, showing one section of related content at a time.

Tabs divide material that belongs to one subject into parallel sections and reveal one of them. The row of labels stays visible permanently, which is the point: it is a map of what else exists, readable without scrolling and without clicking. The metaphor comes from index cards in a drawer, and the implied depth — one card in front, the others immediately behind — is what makes switching feel cheap rather than like navigation.

Because a tab switch changes only what is displayed, it must never save, submit or reload anything. A reader who clicks a second tab expects to click back and find the first one exactly as they left it. Labels stay to one or two words so that the whole row fits on a single line; a row that wraps, or scrolls sideways, has stopped being a map.

Use when

  • Sections are siblings: equal in rank, rarely needed together.
  • There are between two and about six of them.
  • The reader benefits from seeing what else is available.

Avoid when

  • The content must be compared side by side — tabs hide it.
  • The sections form a sequence; steps need a wizard with an order and a sense of progress.
  • Only one section really matters and the rest are filler.

Keyboard A tab row is one stop in the tab order, not one stop per tab. Arrow keys move between the labels; the Tab key jumps past the whole row to the panel. This pattern is called a roving tabindex, and it is why the unselected tabs carry tabindex="-1".

05

Button

A control that performs an action in the current context: it saves, sends, calculates, deletes, opens.

A button changes state rather than location. That single sentence settles nearly every argument about whether something should be a button or a link. The distinction is not cosmetic: browsers treat links as addresses, offering to open them in a new tab, copy them, or return to them with the back button, and none of that makes sense for an action that has already happened.

Buttons also carry rank. Filled, outlined and plain-text buttons form a visual hierarchy, and one filled button per region is enough to say what the expected move is while leaving the alternatives reachable but quiet. Labels should name the action with a verb: "Save changes" still makes sense read aloud out of context, whereas "OK" and "Submit" mean nothing without the sentence above them. Destructive actions look different from the rest, and when they cannot be undone they ask for confirmation.

Use when

  • Something happens on this page: submitting, calculating, toggling, opening a dialog.
  • The action needs ranking against neighbouring actions.
  • The result may take time and needs reporting back.

Avoid when

  • The address changes — that is a link wearing a button's clothes.
  • Several filled buttons compete in one area and none reads as primary.
  • It is disabled with no explanation of what would enable it.

Detail Always set type. A button inside a form defaults to type="submit", so a "Cancel" button with no type will cheerfully submit the form it was supposed to abandon.

06

Text label

Static text attached to another element: the name above a field, the rule beneath it, the verdict after it.

A label is the only element here that does nothing on its own. Its whole function is to give meaning to something adjacent. An unlabelled field is a box whose purpose must be inferred from surrounding context, and that inference fails the moment the context scrolls off the screen, or the page is read by something that cannot see layout at all.

Three kinds of text do this work. The label names the control. Helper text states a rule in advance — the accepted format, the minimum length, what the value will be used for. Status text reports afterwards what happened, and when something failed it says what to do about it, because "Invalid input" tells the reader only that they have been judged. In HTML the first of these is a real <label for="…">, and the connection it makes has a practical side effect: clicking the words focuses the field or ticks the box, which enlarges a small target into a comfortable one.

Use when

  • Any input exists — there are no exceptions worth making.
  • A constraint should be known before it is broken.
  • An action has finished and its outcome needs stating.

Avoid when

  • A placeholder is standing in for the label.
  • The label restates the obvious next to a clearly named field.
  • Required markers are used when almost everything is required — mark the optional ones instead.

Accessibility for must match the input's id exactly; aria-describedby attaches the helper text so it is read out along with the field name rather than skipped.

07

Link

Text or an image pointing at an address — another page, a place on this page, a file, an email client.

The link is the oldest element on this list and the one the web was built around. It changes location rather than state. Everything the browser gives a reader for free follows from that: opening in a new tab, copying the address, bookmarking it, going back. Rebuilding a link out of a div and a click handler throws all of it away.

Link text should describe its destination well enough to survive being removed from the sentence, because assistive software can list every link on a page in isolation, and a list of twelve items all reading "click here" is worthless. Underlines matter for the same kind of reason: colour alone disappears in greyscale printing and for readers who cannot distinguish the hues used. The visited state, often stripped out for tidiness, quietly tells a reader which of a long list of results they have already tried.

Use when

  • The destination is a different page, document or position.
  • A file should be downloaded rather than opened.
  • The reader may want the address itself, to share or return to.

Avoid when

  • Nothing is navigated to and the action happens here — that is a button.
  • The text says "here", "this" or "more".
  • A new tab is opened silently, taking the back button away without warning.

Security rel="noopener noreferrer" belongs on every link that opens a new tab. Without it the opened page keeps a reference back to yours and can redirect it.

08

Tooltip

A brief explanation that appears when an element is pointed at or focused, and vanishes when attention moves on.

A tooltip buys space. The interface stays short for the people who already know what they are doing, and the explanation waits for whoever wants it. It is progressive disclosure at its smallest scale: one line, one element, no commitment.

Its weaknesses all follow from the same fact — it is not there by default. It cannot be reached by touch in the ordinary way, it never appears in print, and a reader skimming quickly will not know it exists. Nothing essential can therefore live inside one. A tooltip names an icon-only button, expands an abbreviation, or defines a term of art; it does not hold instructions, error messages, or the rule that would have prevented a mistake.

Use when

  • An icon-only control needs a name.
  • A term or abbreviation needs one line of definition.
  • The information is genuinely optional.

Avoid when

  • The content runs longer than a line — use helper text or a panel.
  • It contains something interactive; a tooltip cannot reliably be moved into.
  • It appears only on hover, making it invisible to keyboard and touch.

Distinction The browser's own title attribute looks like a tooltip but is not a substitute: it is slow to appear, cannot be styled, and is skipped by much assistive software.

09

Dropdown list

A collapsed list that opens to reveal its options and closes once one is chosen.

A dropdown does the same job as a group of radio buttons — one answer out of many — but keeps the options hidden until asked for. It trades visibility for space, and that trade becomes worthwhile once the list is long enough that showing it in full would drown everything around it. The cost is real: an option nobody opens the list to see may as well not exist, which is why a dropdown is a poor place for anything the reader needs to be persuaded by.

Order carries meaning. Alphabetical order suits names and countries; frequency order suits lists with obvious favourites; chronological order suits years. Related options can be gathered under headings with optgroup so a long list can be skimmed by group rather than read line by line. The native control is worth defending against custom replacements, because an operating system already renders it as a full-height picker on a phone, allows typing to jump to an entry, and handles keyboard and screen-reader behaviour that a rebuilt version has to reimplement in full.

Use when

  • There are more than about six options.
  • The options are self-explanatory and need no comparison.
  • Vertical space is scarce and the field is one of many.

Avoid when

  • There are two or three options — show them as radio buttons.
  • Several answers are allowed; checkboxes beat a list that demands a modifier key.
  • The list is enormous; a searchable field with suggestions serves better.

Terminology "Dropdown" is used loosely for three different things: this select control, a navigation menu that opens on hover, and a combo box that filters as you type. Only the first is a form field, and only the first submits a value.

10

Data grid

Records laid out in rows and their attributes in columns, with tools for sorting, filtering and selecting.

A grid exists so that the eye can run down one column and compare like with like. Everything about its formatting serves that: numbers aligned to the right in a single format so digits line up by place value, one row per record with no merged cells, and column headers that stay readable while the body scrolls. A table becomes a grid when the tools arrive on top — sorting by column, filtering by value, selecting rows and acting on the selection at once.

Those tools must report their own state, or the reader loses their place. A sorted column says which direction it is sorted in; a filter says how many rows it is hiding; a selection says how many rows it holds, and whether the total spans pages that are not visible. Beneath the tools there should still be an ordinary HTML table: rows, cells, and real <th> headers scoped to their column, since that structure is what allows a screen reader to announce "City, Lviv" instead of reading a wall of loose values.

Use when

  • Records share the same fields and must be compared.
  • The number of rows is unknown in advance.
  • Bulk actions apply to a chosen subset.

Avoid when

  • There are only a handful of items with one attribute each — a list is lighter.
  • Layout is the only reason for the table; that is a job for CSS.
  • Every column is shown at once on a phone, where a card per record reads better.

Accessibility scope binds a header to its column or row, and aria-sort states the current sort direction. A caption gives the table a name, which is what lets a reader skip it or enter it deliberately.

The ten at a glance

Each element answers one question. Naming that question is usually enough to settle which element belongs in a given place.

Element Question it answers Typical mistake
Radio buttonWhich one of these?Used for a long list
CheckboxIs this true?Used where answers exclude each other

TabsWhich section?Used for ordered steps
ButtonDo it now.Used to navigate somewhere
Text labelWhat is this?Omitted, or not tied to its control

Three decisions that cover most cases

Radio buttons or a dropdown
Both take exactly one answer. Show the options when there are few and their wording matters; fold them away when the list is long and the options speak for themselves.
Radio buttons or checkboxes
Ask whether two answers could be true at the same time. If they could, the shapes are square.
A button or a link
Ask whether the address changes. Something that happens here is a button; somewhere else to be is a link.
